# StoneQR

Free, open-source (MIT), browser-only QR code generator. Brand: StoneQR at stoneqr.app. Tagline: "QR codes set in stone. Generated in your browser, never expire." Sibling of the private SignUpCity product. The dynamic-code hand-off to SignUpCity is shelved as of 2026-09-05 (the link service is on the back burner): the export panel's "Make it editable and trackable" section is removed, and the site's copy no longer says StoneQR offers one; the `?short=` return leg and the ContentForm notice remain dormant for its return. StoneQR itself has no server, no accounts, no database.

## Rules

- Read `plan.md` first; it is the source of truth for scope, architecture, and milestones. Building started 2026-09-02. M1 to M8 are built, including halftone with zoom and crop, the bulk page, and the `?short=` return leg; so are M9 (silhouette tone, built-in shapes, `/photo`), M10 (the UI refresh, its second pass, and style presets, all recorded in `docs/ui-refresh.md`), M11 (the autosaved design, share links, the corner colour, and the "Preset" label, §8f there), M12 (named saved designs with files, §8g, and the offline service worker), and M13 (centre logos resized honestly, a working knockout, and SVG logos, in `docs/logo-plan.md` and §8h and §8i). M14 is built too, Photo QR in colour (§8j and the record under it in `docs/ui-refresh.md`: Code and Background follow through, and a silhouette takes a "Shape" colour through the engine's `ink` option). Still open: the print-and-phone half of `docs/logo-plan.md` Phase 3 (rows C3, L6, M1 to M3 on the Pixel and an iPhone, plus a colour print for L2 and L8); the findings in `docs/audit-2026-09-06.md` (section A, the share-link, bulk-colour, Photo QR dpi, corner-contrast, and transparent-PNG faults, and the Location tile are fixed; the design-file limits are fixed too, with the tiles' rules shared in `lib/generator/pictures.ts`; sections A, B, and C are fixed, C by wiring every option (Photo QR now prints in the code colour, label sheets take the bulk page's colours and width, the test sheet adds the chosen size and picks A4 or Letter, the PDF has no page margin, the EPS and styled SVG carry titles); still open are section F, the copy-versus-code list, and section D, the scan sheets' coverage; a type tile's word has room for six mono characters between `lg` and `xl`); the real-device scan matrix in `docs/scan-matrix.md` (`bun run scan-sheets` builds the printable `docs/scan-sheets.pdf` from `scripts/scan-sheets/`, a Bun server plus a browser page like `bun run og`; it checks its own row IDs against the doc and exits non-zero on drift, so keeping the two in step is enforced, not remembered) and the remaining M7 extras.
- The generator has Basic and Advanced control sets (toggle above the columns, remembered in localStorage). A saved Advanced choice is stamped on `<html>` by an inline script in `app.html` before first paint, and `app.css` hides the tool until the Generator sets `data-hydrated`, so the prerendered Basic markup never flashes; the script's sha256 sits in the CSP in `svelte.config.js`, so change the two together. Anything only Advanced exposes must be listed in `Design.advancedInUse` so Basic can say it is still in force. Style presets are the tiles labelled "Preset" on the page and called looks in code, in `apps/site/src/lib/looks.ts`: a look is matched from the three shape fields, never stored, so Basic sets corner shapes through a look and `advancedInUse` reports "corner shapes" only for a combination no look offers. Basic sizes are the four tiers in `apps/site/src/lib/generator/sizes.ts`; their reading-distance copy derives from `maxScanDistanceM`, so change the rule there, not the words. The Advanced size chips are those same tiers, so a width chosen in one set is still the chosen one in the other; do not give Advanced its own preset list. A hand-set width shows in Basic as a "Custom" row. The halftone feature is called "Artistic QR" everywhere a user can read it (panel heading, notices, docs aimed at users); it was "Photo QR" until 2026-09-12, which older docs and the scan sheets still say, and code, engine, file names, and the `/photo` route keep `halftone` and `photo`. Its copy never offers to take "a logo": that sent people with a logo into the halftone (§8l in `docs/ui-refresh.md`). Basic includes Artistic QR with upload, crop, the three-way tone (Colour, Black and white, Silhouette) with the silhouette's Cut slider, and the built-in shapes in `apps/site/src/lib/glyphs.ts`; dot size, fade, contrast, the Cut percentage readout, and the Across and Down crop sliders are Advanced. The crop box (`components/CropBox.svelte`) is the engine's `imagePlacement` inverted in `lib/crop.ts`; it writes the same three fields the sliders do, so never give it state of its own. The silhouette is the engine's `threshold` option, applied to source pixels before resampling; the two-layer SVG export reproduces every picture adjustment as filters on the original picture, so `imageFilter` in `apps/site/src/lib/halftone.ts` must stay in step with `prepareSource` in the engine. Below `lg` the generator is one column ordered Content, Preview, Logo, Style, Artistic QR, Size and download: the left column's wrapper is `display: contents` there and a block at `lg`, so its two sheets take part in that order individually. Once the preview card scrolls away, `PreviewBar` pins a thumbnail, the decode badge, and the primary download to the bottom of a phone screen; it is rendered by `ExportPanel` because that is where the export actions live, it watches `#preview-card` and `#generator` so it never covers the footer, and it is hidden at `lg`. Page heroes render inside the Generator's `hero` snippet; the heading shares a row with the Basic/Advanced toggle from `lg` up and stacks above it below that. Keep the row a breakpoint rule, never a flex-basis that happens to exceed phone widths: a hero given `flex-1` collapses to about 64 px next to the toggle on a 375 px screen. The landing pages (`/wifi`, `/vcard`, `/event`, `/logo`, `/photo`) are the same generator with a type preselected or a panel opened: the type picker is never locked, and one `Design` instance is shared across client-side navigations (module state in `Generator.svelte`), so a nav click only changes the type and keeps size, style, and typed fields. Nav links preload their code eagerly and the hero reveal animation runs only on the first load, so navigation must stay fetch-free and instant. The preview label and decode badge live in a caption strip at the bottom of the preview card so its top edge stays flush with the Content and Size cards.
- The centre logo has its own panel, `LogoPanel.svelte`, first in the design column and open from the start, because it is the customisation most people arrive for and it was lost as the third group of a folded Style panel. Dropping a logo while Artistic QR is on switches the blend off (the picture is kept) and says so; while the blend is on, the panel's controls are disabled and offer "Show the logo instead". Under the drop tile sit twelve built-in icons from `lib/logo-icons.ts` (generic marks, never brand logos): ink only, drawn in `Design.fg` and kept following it by an effect in `LogoPanel`, identified by `logoName` ("WiFi (built-in icon)"), so a share link keeps an icon while dropping uploaded pictures and `fromFile` rebuilds one from its name rather than the file's markup. Their data URL must stay base64, because the renderer inlines only that form as markup and places anything else as an `<image>`. They are not the Artistic QR shapes in `glyphs.ts`, which are silhouettes on white; `bun run logo-fixtures` decodes every icon at 20% and 32% as the panel places it, and scan-sheet section `N` puts four of them on paper (N1 to N4, not yet scanned on a phone). The centre logo is sized as a fraction of the code's width (`Design.logoWidth`, 10% to 32%, default 20%), never as an area. The styling library takes no size: its `imageOptions.imageSize` is a coefficient of the error-correction budget, so `lib/logo-size.ts` ports the library's own `calculateImageSize` to predict the hole and `fitLogo` searches for the coefficient landing nearest the width asked for. Only odd module counts are reachable, so the readout reports the width achieved, never the width requested; `apps/site/test/logo-size.test.ts` pins the port against numbers measured from the library's output, so regenerate nothing there without re-measuring. The warnings use `Design.logoCover`, hidden modules over that same budget (`LOGO_WARN_COVER` 0.15, `LOGO_BLOCK_COVER` 0.20), not an area ratio. "Clear space behind the logo" is the library's `center` mode against `overlay`: on cuts the modules out, off paints the logo over them and forces the margin to nought, so the Margin slider is hidden. `Design.logoAspect` is measured from the picture by the Preview, because the hole's shape follows the picture's. The logo tile takes PNG, JPEG, WebP, and SVG; Photo QR still takes pixels only. An uploaded SVG is a document, not a picture, so `lib/logo-svg.ts` (dynamic import, kept out of the first chunk) rebuilds it: inert (script, animation, links, `on*`, and every reference off the machine removed), self-contained (`<style>` rules inlined onto their elements and classes stripped, because SVG style rules are document-wide and would restyle the page around the preview), sized (a viewBox guaranteed, and `width`/`height` set to match so every browser reports one intrinsic size), clipped to that box (the renderer sets `overflow="visible"`), and scoped (`lg-` on every id, so a logo carrying `mask-dot-color` cannot shadow the renderer's). Whatever it changed is said under the tile in the info style. A `.stoneqr.json` design file is untrusted too: `SavedDesigns` rebuilds an SVG logo from one, and `fromFile` refuses an SVG in the Photo QR slot. An SVG logo stays vector into the SVG download; never route it through a canvas on the way in. The string helpers are tested in `apps/site/test/logo-svg.test.ts`; the DOM half is `bun run logo-fixtures`, a Bun server plus browser page over `apps/site/test/fixtures/logos/`, which prepares each fixture, checks nothing active or remote survived, then places it in a real code and decodes it. The scan sheets cover all of this (`C3` the widest allowed logo, section `M` the SVG rows, `L6` a logo over the modules), and `bun run scan-sheets` checks its row IDs against `docs/scan-matrix.md` and exits non-zero on drift or a failed decode, so that pairing is enforced rather than remembered. Those five rows have not met a phone yet; `docs/logo-plan.md` phase 3 says what the next print owes.

The colour fields are Code, Background, and Corners, plus Shape in the Artistic QR panel while the tone is Silhouette ("Ink" and "Paper" remain only in prose and on `/bulk`). `Design.shapeColor` is a plain colour with its own default and no link to `fg`: it briefly followed the code colour the way `cornerColor` does, which let a colour chosen as one end of a gradient reach the shape while the Style panel was disabled (§8k in `docs/ui-refresh.md`). The engine's `ink` option paints only the silhouette, never the dots or the function patterns, so it cannot change what a scanner reads; a heart was decode-checked at every grey from 0 to 255 to establish that. The one check on it is `shapeContrast`, the shape against the paper, at `SHAPE_CONTRAST_MIN` (3, the WCAG bar for a graphical object) and worded as appearance, not scanning; never warn that a shape resembling the code colour is a fault, because that is the classic silhouette. A shape much darker than the code drives the fallback ladder to its last rung and makes the picture faint, which the ladder's own note already says, so do not add a predictive rule for it. The shape stays out of the Style panel's contrast badge, which is the code's print-safety. Any new colour field must go in `PERSISTED`, `COLOUR_KEYS`, and `NULLABLE` in `persist.ts`. `Design.cornerColor` is null while the corners follow the code colour; the styled renderer paints the finder patterns with it, solid, in place of the gradient, and every contrast and sizing check uses `Design.weakestFg`, the worse of the two against the background. The design persists as you work: `lib/generator/persist.ts` keeps the `PERSISTED` fields in localStorage (`stoneqr.design`) and the logo and Photo QR source in IndexedDB, restored synchronously at module scope in `Generator.svelte` before the first render; "Start over" at the right end of the Content heading, shown only once something is set, clears both. Share links are the same record, defaults dropped, as `#1.` plus deflated base64url JSON (`#0.` plain where CompressionStream is missing); a design fragment wins over the saved design on a full page load, never carries pictures, and is stripped from the address bar once applied. Add any new user-set field to `PERSISTED` or it will not survive a reload; `apply` only accepts values whose type matches the current one, and the tests in `apps/site/test/persist.test.ts` pin the format. Named saved designs are `lib/generator/saved.ts` and the modal `SavedDesigns.svelte`, opened from "Save" / "Saved (n)" in the Content heading: the same record plus both pictures in IndexedDB (database version 2, stores `designs` and `designImages`, one transaction per save), never localStorage, with `stoneqr.opened` remembering which one the working design came from so the card can say Update; "Download file" / "Open a design file…" move a `.stoneqr.json` (record and pictures) out and back in. Bump the IndexedDB version in `persist.ts` only by adding stores, never by renaming them. Notes in `docs/ui-refresh.md` §8g, tests in `apps/site/test/saved.test.ts`.
- Code and Background are the only Style settings that apply whichever renderer is in charge, so they sit outside the fieldset a photo disables; Corners, the transparent toggle, Fill, the shapes, and the frame are inside it, and the Logo panel disables its own controls the same way. A setting that is in force must never be disabled. Controls are built from the shared primitives in `apps/site/src/lib/components/`, not styled inline: `SectionHeader` (every panel heading; collapsible ones carry a one-line summary of what is set inside, so folding hides nothing), `Slider`, `Swatches`, `ColourField`, `DropTile`, `Icon`, plus `.subhead`, `.row`, `.chip`, `.toggle`, and `.swatch` in `app.css`. Anything that changes how the code looks is picked from a drawn tile rather than a word; the drawings come from `shape-art.ts` via `QrArt.svelte`. Every colour a user can set, `/bulk` included, is a `ColourField`; there is no `<input type=color>` on the site. `ColourField` opens `ColourPopover`, a modal `<dialog>`, chosen because the browser makes the rest of the page inert, so a click outside closes the picker and is swallowed instead of pressing whatever sits underneath. Do not swap it for the Popover API or a document click listener, which both let that click through. A colour must also be typeable: `ColourField` and the card each carry a hex box, and every path in runs through `normaliseHex` in `lib/colour.ts` (3 or 6 digits, `#` optional, normalised on blur, `null` for anything else, so a half-typed value never reaches the design). Never bind a raw text input to a colour; `/bulk` did until 2026-09-06 and printed whole batches black, item A7 of `docs/audit-2026-09-06.md`. One focus ring and one disabled treatment live in `@layer base` in `app.css`, so do not add per-component ones. Anything that carries `role="radio"` (the type tiles, `Swatches`) uses a roving `tabindex` and the `radioKeys` action from `components/radiogroup.ts`, so the arrow keys work; `.toggle` inputs carry `role="switch"`. Export failures are shown as a notice under the download buttons, never a native `alert`. The design contract and the record of what each phase settled are in `docs/ui-refresh.md`.
- The call-to-action frame is our own SVG wrapper in `apps/site/src/lib/styled.ts`; do not reintroduce the styling library's border plugin (it sizes text as the whole code and needs a separate lazy chunk). Framed art is taller than wide: exports and the decode check go through the aspect-aware `svgToCanvas` and `Design.styledScale`.
- Halftone PNG export renders and encodes in `apps/site/src/lib/halftone.worker.ts`. Anything posted to it must be plain data (use `$state.snapshot` on reactive objects). Keep `renderHalftone` allocation-free in its inner loops; a 4096 px raster should stay around 200 ms.
- Commands from the root: `bun install`, `bun run dev`, `bun run test` (vitest: engine, then the site's pure modules), `bun run check` (svelte-check), `bun run build`, `./deploy.sh` (wrangler pages deploy, then it polls every hashed asset on stoneqr.app until all are served and warms them; do not open the site before it prints its final line, because a request for a not-yet-replicated asset is cached for a year by `_headers`). `apps/site/src/routes/404` prerenders to `404.html` so Pages answers a missing path with a 404 rather than `index.html`; keep it out of the sitemap and the OG routes. Bun uses isolated installs here, so packages live under `apps/site/node_modules` and `packages/engine/node_modules`, not the root.
- The engine's `index.ts` deliberately does not export the pdf-lib modules; import `@stoneqr/engine/export/pdf` and `@stoneqr/engine/labels` lazily from the site so the core chunk stays small (currently about 85 KB gzipped on the generator page, budget 150 KB).
- Golden files pin the hand-built renderers byte for byte: `packages/engine/test/golden/` (single-path SVG and EPS) and `apps/site/test/golden/` (the call-to-action frame). When a renderer change is intended, read the diff, then regenerate with `UPDATE_GOLDENS=1 bun run test`; never regenerate to make a red test go away.
- Open Graph cards are one PNG per route in `apps/site/static/og/`, drawn by `bun run og`: a Bun server plus a canvas page in `scripts/og/`, using the site's own fonts and the engine's matrices, so each card carries a scannable code to its own page. `/` keeps the hand-made `static/og.png`. A new route means an entry in `scripts/og/routes.mjs` and a `bun run og` run, which rewrites the generated `apps/site/src/lib/og-images.ts`; the site tests check the sitemap, the manifest, the files, and that every card still decodes.
- Claims about competitors or physics that appear on the site are tracked in `docs/claims.md`; verify before changing marketing copy.
- Search and sharing plumbing: `Seo.svelte` emits canonical, Open Graph, and a JSON-LD graph (WebSite + WebPage; the home page adds the `WebApplication` node from `lib/schema.ts` through the `schema` prop). `scripts/sitemap.mjs` writes `sitemap.xml` from the Open Graph route list with git `lastmod` dates and `deploy.sh` runs it before every build, so never hand-edit the sitemap. `scripts/icons.mjs` draws `favicon.ico`, `apple-touch-icon.png`, and the manifest icons from the `favicon.svg` design; change the SVG, then `bun run icons`. `static/.well-known/security.txt` expires 2027-09-01 and must be renewed. The launch and distribution punchlist is `docs/launch.md`.
- Fonts: `scripts/fonts.mjs` (`bun run fonts`) subsets the three families to basic Latin and the axis ranges `app.css` uses (Fraunces pinned at weight 500, opsz 18 to 72; mono 400 to 500) and writes `static/fonts/*.woff2`, the generated `lib/fonts.css` and `lib/fonts.ts`, and a marked `Link:` block in `static/_headers` that Cloudflare sends as Early Hints. The fontsource imports stay as the fallback for other characters. If a new weight or axis value is used, change the script's `FAMILIES` and rerun it, or the text falls back to the fuller fontsource file. Do not inline the stylesheet; `docs/performance.md` has the measurements and the critical path.
- The site is an installable PWA that works offline. The service worker is `apps/site/src/service-worker.ts`, built by SvelteKit to `/service-worker.js` and registered from its own hashed init script, so there is no registration code in the app and no CSP hash to keep. The pure rules live in `apps/site/src/lib/sw-scope.ts` and are pinned by `apps/site/test/service-worker.test.ts`. One cache per build (`stoneqr-<version>`, about 1.7 MB) holds all of `build`, the two worker chunks the install step finds inside the bundle (Vite's manifest never lists them), the fonts, the manifest and icons, and every prerendered page; `/og/*`, `og.png`, `sitemap.xml`, `robots.txt`, `llms.txt`, `.well-known/*`, and `_headers` are excluded and never cached. Install stores only OK responses and fails whole on a 404 so a not-yet-replicated deploy cannot wedge the app; pages are network-first with a 3 s timeout, hashed files cache-first, other origins untouched, and nothing a user types ever enters the Cache API. A new build waits behind the running one until the "A new version of StoneQR is ready" banner in `+layout.svelte` is clicked. The `/service-worker.js` `no-cache` rule in `static/_headers` and the warm list in `deploy.sh` must stay in step with it; `docs/pwa.md` has the details and the offline test steps. In `vite dev` the worker is inert.
- Nothing a user types may leave the browser in static mode. No server-side payload handling, ever.
- Every download must pass a decode check. Print safety is a feature, not polish.
- Stack: SvelteKit (Svelte 5) with adapter-static, TypeScript, bun workspaces, vitest; deploy as Cloudflare static assets with wrangler. Engine lives in `packages/engine` as `@stoneqr/engine`.
- Libraries: `uqr` for encoding, `@paulmillr/qr` for decoding with `jsqr` as a lazy fallback (the primary decoder misses about 1 valid symbol in 500), `@liquid-js/qr-code-styling` (lazy) for styled output, `pdf-lib` for PDF, hand-written EPS and pHYs. Do not add `sharp`, `node-canvas`, `jsdom`, or `@qr-platform/qr-code.js`.
- Research and sources: `docs/research/qr-technical.md`. Artistic QR techniques (halftone vs QArt bit steering vs diffusion), the library evaluation, and the decisions live in `docs/research/artistic-qr.md`: the silhouette tone is built, QArt is deferred behind a phone-scan spike, diffusion is rejected.

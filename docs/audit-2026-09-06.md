# Generator audit, 2026-09-06

A read-through of the shipped generator after M13, looking for three classes of fault: options the
engine supports that the site never passes (the class the Photo QR colour gap belongs to, now
M14), places where what is downloaded differs from what was previewed or decode-checked, and
records the site accepts without checking. Every item below was verified by reading both sides
of the call, not from prose. Items marked fixed were done the same day; the order is by what a user would hit
first. Line numbers are as of this date and the uncommitted M13 work.

## A. Things that break or lie

1. **Fixed 2026-09-06.** ~~A share link with an unknown `type` kills the generator.~~ `accepts` now checks the seven enumerated keys (`type`, `eccChoice`, `unit`, `dot`, `cornerSquare`, `cornerDot`, `gradient`) against sets built from their types, and `buildPayload` ends with an empty result as a second fence; pinned in `persist.test.ts` and checked live with a `#0.` link carrying `"type":"bogus"`. The original finding: `accepts` in
   `apps/site/src/lib/generator/persist.ts:101-109` only checks that a value's `typeof` matches
   the current one, so `type` takes any string. `buildPayload` in
   `lib/generator/state.svelte.ts:396-472` is a switch with no `default` and no return after the
   `try`, so an unknown type returns `undefined`, `payloadResult.payload` throws inside a
   `$derived`, and every derived below it (`qr`, `plainSvg`, `status`) is dead: a blank tool with
   no message. The `#0.` form of a link is plain JSON, so a mistyped or hostile link is one edit
   away. The design-file path is safe by accident (`SavedDesigns.svelte` overwrites `type` with
   the validated one). `unit`, `dot`, `cornerSquare`, `cornerDot`, `gradient`, and `eccChoice`
   are the same class but degrade rather than throw.
   *Fix:* `accepts` checks the enumerated keys against their lists, and `buildPayload` ends with
   a `default` that returns the empty result. Pin both in `persist.test.ts`.
2. **Fixed 2026-09-06.** ~~A share link leaves the recipient's own pictures behind.~~ A fragment apply now deletes both pictures from IndexedDB and clears the `halftone` flag (item 11 with it); checked live by seeding both stores, opening a link, and reloading plain. The original finding: `Generator.svelte:104-116` clears `design.logo` and `design.halftoneImage` when a
   fragment applies, then returns before reading IndexedDB, so the `stored` record still says
   `undefined` for both; `keepImage` (`:133-137`) sees no change and never deletes. The fragment
   is stripped by `replaceState`, so the next plain load takes the saved-design path and attaches
   the old logo to the shared design, with `logoName` now empty. This is exactly what the comment
   above the function says it prevents.
   *Fix:* on a fragment apply, delete both images (`writeImage(key, undefined)`) and set `stored`
   to match, or mark `stored` so the first `keepImage` writes.
3. **Fixed 2026-09-06.** ~~The bulk page's decode check ignores the chosen colours.~~ The colours travel in `EncodeOptions`, `decodes` rasterises in them, a colour change clears the run like a content change, and the unverified notice says the check used the colours above; checked live with grey on grey (six of six fail) against black on white (six pass). The original finding: `lib/bulk/worker.ts:58-61`
   rasterises every row black on white for the check, while the ZIP is rendered with the page's
   `fg` and `bg` (`:162-174`). Red on pink passes every row and `manifest.csv` says verified.
   The hard-coded quiet zone there is documented and intended; the colours are not.
   *Fix:* pass the same `fg` and `bg` to `rasterize` in `decodes`.
4. **Fixed 2026-09-06.** ~~A Photo QR PNG can open at the wrong physical size.~~ The size arithmetic is `lib/generator/halftone-png.ts`, which returns the dpi that prints the capped raster at the chosen width; the export writes it, the Advanced ticket and hint say so when the cap holds, and `halftone-png.test.ts` pins that every case opens at the requested width. Checked live at 250 mm and 600 dpi: 4081 px, 415 dpi. The original finding: `ExportPanel.svelte:53-63` caps the
   raster at 4096 px a side and floors the pixels per module, but `halftonePng` writes the
   *requested* dpi into `pHYs` (`lib/halftone-export.ts:98`, `halftone.worker.ts:40`). A 250 mm
   code at 600 dpi wants 5906 px, gets 4081, and opens at about 172 mm. The engine's own
   `exportPng` recomputes an effective dpi from the pixel count for this exact reason
   (`packages/engine/src/export/png.ts:236-238`).
   *Fix:* write `widthPx / (widthMm / 25.4)` as the dpi, as `exportPng` does, and say in the
   button label when the cap has been hit.
5. **Fixed 2026-09-06.** ~~A pale corner colour on a transparent background is never contrast-checked.~~ The rule is now `weakestForeground` in `lib/generator/contrast.ts`, comparing both colours against `paperColor(bg)`, so transparent means white; the Style panel's badge shows in that mode and says "on white" in Advanced; `contrast.test.ts` pins that pale corners on transparent are no longer print-safe. The original finding: `weakestFg`
   (`state.svelte.ts:213-216`) returns the code colour whenever `transparentBg` is on, but
   `assess` and `summary` are given `bg: 'transparent'`, which `paperColor` in the engine treats
   as white. So paper is white for the assessment and the corner colour is left out of it: light
   finder patterns raise no warning and never block the download. `StylePanel.svelte:61` also
   blanks the contrast badge in that mode.
   *Fix:* `weakestFg` compares both colours against `paperColor(bg)` rather than bailing out.
6. **Fixed 2026-09-06.** ~~The plain PNG fills a transparent background with white and says nothing.~~ `rasterize` takes `transparent`, writing light pixels white with alpha 0, `exportPng` accepts `bg: 'transparent'` like the SVG renderer, and the export panel passes `design.bgColor`; the engine test decodes the transparent file and checks both a quiet-zone and a finder pixel. The original finding:
   `ExportPanel.svelte:137` passes `#ffffff` when `transparentBg` is on. The preview shows a
   checkerboard, and the SVG, PDF, EPS, and the styled PNG all honour transparency; only this
   path differs. `encodePng` already writes RGBA; the limit is `rasterize`
   (`packages/engine/src/raster.ts:37` hard-codes alpha 255).
   *Fix:* give `rasterize` a transparent-background option that writes alpha 0 for light pixels,
   or at least say under the button that the PNG will be on white.

## B. Records the site accepts without checking

7. **Fixed 2026-09-06.** ~~A design file can carry a 24 MB TIFF into the decode path.~~ The tiles' types and sizes now live in `lib/generator/pictures.ts` and `fromFile` holds each slot to the same rule through `dataUrlProblem`, measuring a data URL by what it decodes to; a picture that fails is left out and the open-file dialog stays up to say which and why. Two neighbours found on the way and fixed with it: a built-in shape is an SVG in the Photo QR slot, so the M13 refusal lost it on the way back through a file (it is now rebuilt from `glyphs.ts` by the name in the record, never taken from the file), and the dialog was saving the file's own SVG logo into IndexedDB rather than the rebuilt one. The GIF discrepancy in item 20 closed with the shared list: the logo tile now refuses GIF, as every piece of copy said. Tests in `pictures.test.ts` and `saved.test.ts`. The original finding: `saved.ts:52` allows 24 MB and
   `isPicture` (`:258-260`) accepts any `data:image/*`, while the tiles enforce 2 MB and
   PNG/JPEG/WebP/GIF/SVG for the logo (`StylePanel.svelte:127-134`) and 8 MB and PNG/JPEG/WebP
   for Photo QR (`HalftonePanel.svelte:51-58`). The SVG refusal added in M13 is right; size and
   format parity is still missing.
   *Fix:* `fromFile` applies the tile limits per slot and reports which one failed.
8. **Fixed 2026-09-06.** ~~`accepts` skips its own limits for fields whose default is null.~~ The finite and length checks now run whatever the current value is, and the six colour fields must be hex; pinned in `persist.test.ts`. The original finding: `persist.ts:104` returns
   early for `cornerColor` and `shortUrl`, before the finite-number and 20 000-character checks.
   A link can put a megabyte string in either; the autosave then exceeds the localStorage quota
   and `writeSaved` swallows the error, so the design silently stops persisting. The nullable
   fields are otherwise handled correctly in both directions.
   *Fix:* run the string and number checks on that branch too, and validate `cornerColor` as a
   hex colour.
9. **Fixed 2026-09-06.** ~~The restored logo aspect is thrown away on every load.~~ The Preview no longer resets the aspect when the logo is merely absent; clearing the logo, Start over, and a share-link apply reset it instead. The original finding: `Preview.svelte:119-125` sets
   `logoAspect = 1` whenever `design.logo` is falsy; on a reload the logo arrives from IndexedDB
   after the settings, so the value `apply` just restored is overwritten and then autosaved as 1.
   It self-heals once the picture is measured, but `logoAspect` in `PERSISTED` is dead weight and
   `logoFit`, `logoCover`, and `logoBlocked` run against a square for the length of the round
   trip.
   *Fix:* reset the aspect only when the user clears the logo, not when it is merely absent.
10. **Fixed 2026-09-06.** ~~Picture writes fail silently for the working design.~~ `writeImage` now rejects and `writeSaved` returns false, and the Generator shows a notice above the tool saying what the browser could not keep and that a design file from Saved keeps it. The original finding: `Generator.svelte:136` and
    `persist.ts:181` discard IndexedDB errors, so an 8 MB photo on a full store is dropped with
    no message: after a reload the settings are back, the picture is gone, and `halftone` is
    still true. `SavedDesigns` reports the same failure properly through `fail()`.
    *Fix:* surface a notice the way the export panel does.
11. **Fixed with item 2.** ~~`compact` keeps `halftone: true` in a link that carries no picture.~~ Low impact:
    `halftoneActive` gates on the image, so nothing renders wrong; it only leaves a stale flag in
    the recipient's autosave. Clear it alongside the image when a fragment applies.

## C. Engine options no site path passes

Found by grepping every option name across `apps/site/src` and `scripts`. Each is a feature gap
rather than a bug, and each is the same shape as M14. **All wired 2026-09-06** except the two
noted; what each became is under its bullet.

- `HalftoneOptions.dark` and `.light`: M14. *Done, the first half:* the Preview passes the Code and Background colours, and the worker, the SVG download, and the decode check copy them, so Photo QR and the built-in shapes now print in the code colour. The second half, a Shape colour of its own, stays M14.
- `LayoutOptions.codeSizeMm`, `.fontSizePt`, `.cmyk` for the label sheets, and `labels.ts:187`
  hard-codes the ink to black. The bulk page's colour and width controls change the ZIP and do
  nothing to the label PDF (`routes/bulk/+page.svelte:246`). The engine has no colour option
  here at all, so this needs one before the page can pass it. *Done:* `LayoutOptions` takes `fg`
  and `bg` (black stays 100% K, captions stay black, a white or transparent background draws
  nothing), `labelColours` is tested, and the bulk page passes its colours and width, which the
  engine holds to what the label allows; the page's copy says so. `fontSizePt` stays the default:
  there is no control for it and 8 pt fits every sheet.
- `TestSheetOptions.sizesMm` and `.pageSize`: the test sheet is always 15, 20, 30, and 50 mm on
  US Letter (`ExportPanel.svelte:172`), whatever size and unit the design has. The four-size
  ladder is the point of the sheet, but the chosen size should be on it and an A4 user should
  get A4. *Done:* `lib/generator/test-sheet.ts` adds the chosen width to the ladder when it is
  not there and is 100 mm or under (a larger code would not share the page; the plain PDF is
  for that), and picks Letter for inches or a Letter-region locale and A4 otherwise; both
  sheets take it, tests in `test-sheet.test.ts`. The home page's "four sizes" is item 13's to fix.
- `PdfOptions.marginMm`: always the 5 mm default, so the PDF page is wider than the preview
  suggests. `EpsOptions.title` and `.cmyk`: the PDF gets "QR code: <type>" as its title, the EPS
  keeps the generic one. `EncodeOptions.maxVersion`: unused. *Done:* the PDF is exported with no
  margin, so its artboard is the code's printed width like the SVG and EPS (the scan-matrix file
  table says so), and the EPS carries the same title as the PDF. `maxVersion` stays unused on
  purpose: the site sets a minimum version and lets the content decide the rest.
- The styled SVG carries no `<title>` (`lib/styled.ts:121`); the plain SVG and the bulk SVGs both
  set one. *Done:* `StyleOptions.title`, written after the root tag, passed from the Preview.

## D. What the scan sheets cannot see

`scripts/scan-sheets/page.ts` never sets `cornerColor`, a transparent background, a quiet zone
other than 4, or any halftone colour, so items 4, 5, and 6 and M14 have no row. Its styled
decode check uses 10 px per module with no retry where the site uses 8 px plus a 2× retry
(`Preview.svelte:210-218`), so a borderline design can pass one and fail the other. Add a corner
colour row and a coloured silhouette row (the latter is in the M14 plan), and align the check
with the site's.

## E. Dead code

`clampInt` in `packages/engine/src/render/halftone.ts:456` is never called.

## F. Copy that contradicts the code

12. **`advancedInUse` misses the module shape.** `state.svelte.ts:257-258` reports "corner shapes"
    only when a corner row is non-square, but the Modules swatch (`StylePanel.svelte:263`) is
    Advanced-only and no preset in `looks.ts` pairs a shaped module with square corners. Set
    Modules to Rounded, leave the corners square, switch to Basic: no preset tile is selected, the
    code renders rounded modules, and the "Advanced settings still apply" notice never fires.
    That breaks the rule in `CLAUDE.md`. *Fix:* a `dot !== 'square'` arm, reported as "module
    shape".
13. **The home page promises exports Basic does not offer.** `routes/+page.svelte:35-38` lists
    SVG, PDF with 100% K black, EPS, and a four-size test sheet. EPS and the test sheet exist
    only in the Advanced branch of `ExportPanel.svelte` (`:440-460`), and Basic is the default.
    "100% K" holds only for unstyled designs; a styled PDF is a raster and its ticket says so.
    `README.md:7` and `static/llms.txt:3` ("PDF (CMYK)") overreach the same way. *Fix:* say
    "in Advanced" for EPS and the sheet, and "100% K black for the plain style".
14. **`/open-source` tells readers no third-party request exists.** `routes/open-source/+page.svelte:25`:
    "the only requests are the page's own scripts, styles, and fonts", but the CSP in
    `svelte.config.js:26,30` allows the Cloudflare Web Analytics beacon, which loads and posts.
    `/privacy` discloses it; the page that tells people to open the Network tab does not, so a
    reader following the instructions sees a request the page said would not be there. *Fix:*
    name the beacon there too, and that it carries no content.
15. **The Photo QR summary hides most of the panel.** `HalftonePanel.svelte:40-44` returns only
    the picture name and the tone. Zoom, Across, Down, Cut, Dot size, Fade, and Contrast are all
    set inside and none is named, so folding the panel hides a non-default Cut or crop, against
    the `SectionHeader` contract. The Style panel's summary is the model to copy.
16. **Retired words on controls.** `HalftonePanel.svelte:175` has a "Look" subhead where the
    site says "Preset"; the Cut slider's end labels (`:188-189`) and its hint say "Ink" and
    "Paper" on a control, which the colour rule reserves for prose and `/bulk`. Arguably tone
    rather than colour; decide, then make the panel match.
17. **`/never-expires` still trails the shelved hand-off.** `routes/never-expires/+page.svelte:55`
    says a hand-off to a link service "is planned". It is shelved, not planned; drop the sentence.
18. **`advancedInUse` wording no longer matches the labels.** "scan distance" is the control
    "Read from", "PNG resolution" is "PNG detail", "gradient" is the "Fill" swatch, and "corner
    shapes" are two rows, "Corner frames" and "Corner dots". A Basic user sent to Advanced by the
    notice cannot find the words it used.
19. **`/photo` describes the Advanced path as the default.** `routes/photo/+page.svelte:20` says
    to use "the crop sliders"; in Basic the crop is the drag box plus Zoom, and Across and Down
    are Advanced. `HalftonePanel.svelte:223` says Advanced adds dot size, fade, and contrast, and
    omits Across, Down, and the Cut readout.
20. **Fixed with item 7.** ~~The logo tile takes GIF and says it does not.~~ `StylePanel.svelte:127` accepts
    `image/gif` on drop while the `accept` attribute, the hint, the error text, `/logo`, and the
    README all say PNG, JPEG, WebP, or SVG. Pick one; an animated GIF would render its first
    frame, so refusing is the safer answer.

Checked and correct: the size tiers and their reading distances against `maxScanDistanceM`; the

## G. Layout

21. **Fixed 2026-09-06.** ~~The "Location" type tile overflows its box on a laptop-width window.~~ The tile says "Place" through `SHORT`, and `.type-name` clips with an ellipsis; checked at 1100 px, where "Place" is 29 px in a 46 px tile, the accessible name and title still read "Location", and a forced "Location" label clips inside the tile. The original finding: Reported by Garrett
    on 2026-09-06 with the browser at about 75% of the screen (vertical tabs); reproduced in the
    Browser pane at 1100 px. Between `lg` and `xl` the generator's side columns are 18 rem
    (`Generator.svelte:205`), so the Type group is 253 px, five tiles a row give 46 px each, and
    after the tile's 0.15 rem side padding there is about 41 px for the label. The labels are
    JetBrains Mono at 0.55 rem, uppercase, letter-spaced (`app.css:864-871`): "LOCATION" measures
    47 px, so the N sits outside the tile. Every other label fits, the longest being "MECARD" at
    35 px. Any window between 1024 and 1279 px wide shows it, which is most laptops with a
    sidebar or a not-quite-full window; at `xl` the column is 22 rem and the tile is 55 px, so a
    full-screen desktop never sees it, which is how it shipped.
    *Options considered.* Icons only below `xl`: fixes it, but takes the words off nine tiles
    that fit for the sake of one. Four columns below `xl`: three rows of 4, 4, 2, taller than the
    column has to spare. A 2:2:3:3 reflow with the rarer types on the short rows: the ordering
    would then differ by width, and the arrow-key roving order with it. Shrinking the font:
    it needs 13% and 0.55 rem is already the floor.
    *Fix.* Two parts. First, give the tile a shorter word through the `SHORT` map in
    `ContentForm.svelte:39`, which exists for exactly this ("Calendar event" is "Event" on the
    tile): `geo: 'Place'` reads at 29 px. "Location" stays as the tile's `aria-label` and
    `title`, in the description line under the grid, in `SavedDesigns`, and in the engine, so
    nothing but the six letters on the tile changes. Second, a rule so it cannot happen again:
    `.type-name` gets `max-width: 100%`, `overflow: hidden`, and `text-overflow: ellipsis`, so
    a label that outgrows its tile shows an ellipsis inside the box rather than letters outside
    it, which a review at 1100 px will catch. The budget to remember: at 18 rem a label has room
    for six mono characters, so a new type's tile word must be six letters or fewer, and the
    check is the Browser pane at 1100 px, not a full-width screenshot.

## Clean

Checked and found consistent: `PERSISTED` covers every user-set field; "Update" in Saved
designs writes both pictures in one transaction; opening a design clears a picture the new one
lacks; `stoneqr.opened` is cleared on delete, on another tab deleting, and on Start over; "Start
over" does not flash on load; the halftone SVG and raster share `imagePlacement`; the PNG worker
and SVG download reuse the option set the preview verified; `logoMargin` and the library's
overlay-mode zeroing agree with `fitLogo`; the plain renderer's use of `fg` rather than
`weakestFg` is safe because any corner colour forces the styled path.
